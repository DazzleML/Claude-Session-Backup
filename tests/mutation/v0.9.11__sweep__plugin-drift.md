## The anomaly that came first (and why the first run's numbers were discarded)

The initial sweep reported **10 of 12 `apply-failed`** with "found 0 occurrences" -- despite my having validated all twelve as unique matches minutes earlier. Summary would have read `{"apply-failed": 10, "killed": 2}`.

Root cause: `commands.py` is **8184 CRLF line endings, zero bare LF**. The harness compares against `read_bytes()`, so a spec `\n` cannot match a file `\r\n`. My pre-validation had used text mode, which silently normalizes CRLF to LF -- so **the validator was wrong, not the harness**. The tell was in the data: the only two mutants that applied (M3, M6) were the only two whose `original` was a single line with no newline to mismatch on.

Fixed by rewriting every `original`/`mutated` with CRLF and re-validating against undecoded bytes. Two lessons worth keeping:

1. **Validate the way the consumer reads.** A validation that normalizes what the consumer preserves proves nothing.
2. **A low kill rate is a hypothesis, not a finding.** Reporting "2/12 killed" would have indicted a suite that in fact kills 9/12 -- and the caveat below cuts both ways.

Worth noting as a possible harness improvement (not made here -- the harness is the skill's, not this project's): the `found 0` error could name line-ending mismatch as a likely cause when the spec contains `\n` and the target contains `\r\n`.

## Caveats

- A kill proves the suite noticed **this** change, not that it tests the right thing.
- **A clean sweep is evidence about the mutations tried, not proof of suite completeness.**
- Scope was `tests/test_setup_update.py` only. The mutants all lie in code that file exercises, but a broader run could reach callers it does not cover.
