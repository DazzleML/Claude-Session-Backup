# v0.9.1 -- Fix -- pid-capture liveness (#72)

Hand-runnable companion to `tests/test_liveness_pid.py` (22 automated
tests). Verifies the #72 fix on a real machine: registry entries record
their hosting claude PID at SessionStart, and pid-bearing entries verify
by that pid alone -- fresh, forked, and in-app-switched sessions all get
honest tiers, and the ghost `[running]` dies.

**Legend** (for external testers): #72 = the GitHub issue this fixes
(liveness argv mis-attribution); "the registry" = `csb-live/` under your
Claude data dir, one JSON file per open session; "ghost" = a session
shown `[running]` that nothing hosts.

## Prerequisites

- csb at the version carrying this checklist, installed editable or from
  the release.
- **The plugin must be updated for pid capture to switch on** -- the hook
  scripts ship with the plugin, not the pip package:
  `claude plugin update claude-session-backup@dazzle-claude-session-backup`
  (No session restarts needed afterward: hook fires resolve the
  installed plugin at fire time.)

## 1. Pid capture happens (the D1 channel)

- [ ] Open a fresh scratch session: `claude` in some scratch directory.
- [ ] Read its registry entry: newest file in `<claude-dir>/csb-live/`.
      Expect a `"pid"` field whose value is a real process id.
- [ ] `Get-Process -Id <that pid>` (or `ps -p <pid>`) -> a claude
      process. That pid was captured from INSIDE the process tree, not
      scanned.
- [ ] `csb set show current` -> the scratch session shows **[running]**
      -- a bare fresh launch, which argv-matching could never verify.
      (Pre-fix behavior: `[no exit observed]`.)

## 2. The fork child verifies; the parent is not credited (D3)

- [ ] `csb resume <some-closed-session> -- --fork-session` in a fresh
      terminal.
- [ ] `csb set show current --json`: the fork child is `"running"` with
      its own pid; no OTHER member carries that same pid.

## 3. The switch scenario heals at the next hook fire (D2)

- [ ] Resume a session plainly in a fresh terminal; confirm `[running]`.
- [ ] Inside it, `/resume` and switch to a different conversation.
- [ ] `csb set show current`: the abandoned session may keep `[running]`
      briefly -- its entry's pid is still alive and hosting *something*
      (this residual is the documented hook-coverage boundary: the
      switch itself fires no hooks). The moment any hook fires for the
      new conversation (compact, or close-and-reopen), the entries heal:
      pid moves to the new conversation's entry.
- [ ] Close that terminal entirely; `csb set show current`: BOTH
      sessions now honest (entry pid dead -> no `[running]` from the
      stale command line -- pre-fix, the abandoned one stayed a ghost as
      long as ANY process's argv named it).

## 4. Exit and boot-view tiers still work end to end

- [ ] Exit the scratch session from step 1 cleanly. Its registry entry
      disappears; `csb set show boot` shows it `[exited]`.
- [ ] `csb set show current` before/after: counts drop by one; no row
      ever shows a pid belonging to a different session's process.

## 5. Degradation honesty (pid-less entries, old plugin)

- [ ] Hand-remove the `"pid"` key from one live entry (edit the JSON).
      `csb set show current`: that row falls back to command-line
      matching -- same tier it would have had pre-fix; nothing crashes.
- [ ] Restore the entry (re-add the pid or just close/reopen the
      session).

## What the mocks don't cover (why this checklist exists)

- The REAL `process.ppid` value crossing Node -> env -> Python on your
  platform and landing as an integer in the entry.
- Windows CIM `CreationDate` projection to epoch seconds inside the
  PowerShell one-liner (the reuse guard's input) on a real process
  table.
- The installed-plugin resolution: pid capture only works after the
  plugin update; step 1 fails honestly (`[no exit observed]`, no pid
  field) if the old plugin is still installed.
- The switch-heal timing in step 3 -- unobservable in unit tests because
  the switch fires no hooks by definition.
