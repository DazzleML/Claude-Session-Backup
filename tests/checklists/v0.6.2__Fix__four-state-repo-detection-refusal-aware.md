# Human Test Checklist: four-state repo detection -- refusal is not absence

**Target version:** v0.6.2
**Ships with commit:** `v0.6.2: fix: four-state git_repo_state -- refused is not absent (#54)` (TBD -- pre-commit)
**Companion automated tests:** 17 new (1039 pass, 1 skipped) -- `git_repo_state` derivation, refusal wording across banner/backup/check/status/setup/hook, setup's no-init + post-init re-probe guards, `--auto` zero-git-config-mutation, offer default-No + accept-recovery.

## What this is

The 2026-07-22 incident: git 2.35.2+'s dubious-ownership check refused an intact `~/.claude` repo in non-elevated shells (Administrators-owned dir, fresh-box artifact) while elevated contexts committed daily -- and csb reported "has no git repository", then `setup` offered `git init` and contradicted itself one line later. v0.6.2 makes csb say what git actually said. A human runs this because refusal is inherently *environmental*: the automated tests simulate it at the seam, and only a real refused-repo (or a careful simulation) proves the end-to-end reading experience.

## Prerequisites

1. csb v0.6.2 from this working tree; **sandbox Claude dir** as in prior checklists (`--claude-dir <SANDBOX> --db <SANDBOX>/test.db` on every command).
2. **Simulating a real refusal** (pick one):
   - **(a) Ownership route (most faithful; needs a second account or admin):** `git init` the sandbox, then change the sandbox dir's owner to another account (e.g. Administrators via an elevated shell: Explorer > Properties > Security > Advanced > Owner). A NON-elevated shell's git will then refuse it. Confirm with `git -C <SANDBOX> rev-parse --is-inside-work-tree` -> `fatal: detected dubious ownership...`.
   - **(b) Config route (no ownership games):** set `GIT_CONFIG_GLOBAL` + `GIT_CONFIG_SYSTEM` to point at empty temp files and add ONLY `[safe] directory = <something-else>` -- on a machine where the sandbox would be dubious. If neither route yields a real refusal on your box, mark HV.1/HV.2 MANUAL and rely on the seam-level automated tests.
3. **Reset between sections:** restore sandbox ownership / unset the env vars.

## High-Value Verification

### HV.1 -- Banner under refusal: BLOCKED, not "no repository"

- [ ] **Steps** (refusal active): `csb list -n 1 --claude-dir <SANDBOX> --db <SANDBOX>/test.db`
- [ ] **Expected:** banner says `BACKUPS BLOCKED IN THIS SHELL -- a git repository EXISTS at ...`, quotes git (`git said: fatal: detected dubious ownership...`), says `do NOT re-initialize`, points at `csb setup`. It must NOT say "has no git repository" or "nothing is preserved or restorable".
- [ ] **Why:** the false-absence claim was the incident's trust damage; this is the surface users see first.

### HV.2 -- Setup under refusal: diagnosis page, no init, safe offer

- [ ] **Steps** (refusal active, real terminal): `csb setup --claude-dir <SANDBOX> --db <SANDBOX>/test.db`
- [ ] **Expected:** `Git repo: PRESENT -- but git REFUSES it in this shell.` + git's words + ownership-first guidance + the exact `safe.directory` command in cyan. NO `Initialize a git repository? [Y/n]` prompt anywhere. The offer `Run that safe.directory command now? [y/N]` defaults to No (press Enter -> "Re-run `csb setup` after fixing"). Re-run and answer `y`: config written, `git now accepts the repository`, normal checklist renders. **Eyeball:** does the page read as "your data is safe, here's what's wrong" rather than alarm?
- [ ] **Why:** this is the incident's loop, replaced; and consent quality for the config mutation is human judgment.

### HV.3 -- Multiple setup runs are idempotent and safe

- [ ] **Steps:** after HV.2's recovery, run `csb setup` twice more; then remove the safe.directory entry to restore refusal and run twice more.
- [ ] **Expected:** protected runs -> "nothing to set up" + checklist, byte-identical both times, no state changes. Refused runs -> the same diagnosis page both times, no git config growth (check `git config --global --get-all safe.directory` count is stable when declining).
- [ ] **Why:** the user's explicit worry -- "a user might run another setup" -- multi-run must never compound state.

## Full Verification

### FV.1 -- status / check / backup wording under refusal

- [ ] **Steps:** `csb status`, `csb _check`, `csb backup`, `csb backup --no-commit` (all with sandbox flags, refusal active).
- [ ] **Expected:** status: `Git repo:      REFUSED` + `git said:` line (and NOT the absent-state "backups disabled" advice). `_check`: summary names refusal + "do NOT re-initialize" (this text becomes the SessionStart systemMessage). bare backup: rc 1, quotes git, no "is not a git repository". `--no-commit`: indexes fine; `[index-only]` closing line says REFUSES.

### FV.2 -- absent-state regression sweep

- [ ] **Steps:** fresh sandbox with NO `.git`: `csb list` (banner), `csb setup` decline, `csb setup --auto`, `csb status`.
- [ ] **Expected:** byte-identical v0.6.1 behavior -- "NO BACKUP PROTECTION ... has no git repository" banner, init offer present, auto init+backup works, status "Git repo: NO" + advice. The four-state split must not have moved the absent experience.

### FV.3 -- hook log wording

- [ ] **Steps:** `CLAUDE_DIR=<refused-SANDBOX>`, echo the SessionEnd JSON into `hooks/scripts/backup-hook.py`; read `csb-logs/backup-SessionEnd.log`.
- [ ] **Expected:** `[index-only] git REFUSES the existing repo in this context ... do NOT re-init ...` -- not "no git repo". Child still runs `--no-commit` (indexing continues).

### FV.4 -- git-missing state

- [ ] **Steps:** shell with git stripped from PATH: `csb status`, `csb setup`.
- [ ] **Expected:** `GIT ERROR (git was not found on PATH)` / `Git: ERROR` -- never "no repository", never an init offer.

## What mocks don't cover

- A REAL dubious-ownership refusal end-to-end (route (a)) -- automated tests inject the state at the seam.
- Whether the refusal diagnosis page reads as reassurance + instructions (HV.2 eyeball) in a real terminal with colors.
- git's actual stderr wording across git versions/locales passing through legibly.
- Elevation-dependence itself (elevated vs standard shell against the same Administrators-owned sandbox) -- worth one manual pass on a Windows box that allows it.
