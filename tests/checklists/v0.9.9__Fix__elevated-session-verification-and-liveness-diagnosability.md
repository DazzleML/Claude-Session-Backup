# v0.9.9 -- Fix -- elevated sessions verify; liveness explains its negatives

Hand-runnable companion to `tests/test_liveness_pid.py` (36 tests, 4 new). Verifies the fix for a bug that mocks structurally cannot reproduce: a **running** Claude Code session rendering `[no exit observed]` because it was launched from an **elevated** terminal.

**Legend** (for external testers): "the registry" = `csb-live/` under your Claude data dir, one JSON file per open session; "captured pid" = the host process id the SessionStart hook records from inside the process tree; "elevated" = a terminal started with *Run as administrator*; `by_pid` = the scan's pid-indexed map that pid verification consults.

## What was wrong

A process running at a higher integrity level than csb hides its PEB: Windows returns an **empty `CommandLine`** (and `ExecutablePath`) to a non-elevated query, while `Name` still reads. The scan admitted processes to `by_pid` only when the *command line* identified them as claude, so an elevated session was dropped -- and pid verification, the mechanism added precisely to stop depending on argv, silently inherited an argv dependency. Observed live: a whole unreadable ancestry, `claude.exe -> cmd.exe -> WindowsTerminal.exe`, same user, admin terminal.

## Prerequisites

- csb at the version carrying this checklist (`csb -V`).
- Windows, with the ability to open both an elevated and a normal terminal. (The bug is Windows-specific in mechanism; see the cross-platform note at the end.)
- At least one ordinary (non-elevated) Claude Code session open, for contrast.

## 1. The bug, reproduced and fixed (the load-bearing check)

- [ ] Open a terminal **as administrator**. Start a session there: `claude`.
- [ ] In a **normal** (non-elevated) terminal, run `csb set current`.
- [ ] The elevated session appears as **`[running]`**, not `[no exit observed]`.
      (Before this fix it read `[no exit observed]` while plainly running.)
- [ ] `csb set current --json` -> that member has `"live_status": "running"` and a numeric `"pid"`.

## 2. Recorded vs verified are now distinguishable

- [ ] In the same `--json`, every member carries **both** `"pid"` (the verification result) and `"recorded_pid"` (what the entry stored), plus `"pid_at"`.
- [ ] For a healthy session the two agree. Where they differ -- `recorded_pid` set but `pid` null -- that is now readable as "captured, but not verified", which is exactly the distinction whose absence cost an evening of diagnosis.

## 3. Claude Desktop stays out of the roster (regression guard)

- [ ] With Claude Desktop running, `csb set current` shows **no** Desktop processes as sessions, and the roster count matches your actual CLI sessions.
      (The name-based fallback applies ONLY when the command line is unreadable; a readable Desktop command line still excludes it. The first version of this fix got that wrong -- the automated test caught it.)

**What actually keeps Desktop out, precisely** (a sweep flagged the wording above as easy to misread): the scan-level exclusion works on *readable* Desktop command lines. A Desktop process whose cmdline were hidden would be admitted to `by_pid` -- exactly like any other same-named process -- because name alone cannot tell them apart. That is harmless, and the real containment is one layer down: **admission to `by_pid` verifies nothing by itself.** A session only shows `[running]` when a registry entry recorded that exact pid, and Claude Desktop never writes registry entries. Pid reuse by a same-named process is separately blocked by the creation-time guard. So the roster-level guarantee holds for reasons broader than the cmdline check alone.

## 4. Ordinary sessions are unaffected

- [ ] Non-elevated sessions still show `[running]` with their pids.
- [ ] A cleanly-closed session disappears from `csb set current` as before.
- [ ] A session closed with **Ctrl+C** still leaves an entry rendering `[no exit observed]` -- correct, since the SessionEnd hook is cancelled and no exit is observed. (Known behavior, not a regression; tracked separately.)

## 5. The hook now says how it captured the pid

Requires the plugin to be updated (`csb setup update`) -- the hook scripts ship with the plugin.

- [ ] Start a new session, then read `<claude-dir>/csb-logs/backup-SessionStart.log`.
- [ ] The newest line reads like `live-registry: open <id> (source=startup pid=12345 via=walk)`.
- [ ] `via=walk` means an ancestor was identified as the claude CLI (trustworthy). `via=env-fallback` means the walk could not complete and the environment ppid was used -- on Windows often a transient shell, i.e. a pid that may already be dead. `via=none` means no pid at all.
- [ ] If a session's entry ever lacks a pid, the log now says so explicitly instead of being silent.

## 6. Optional: the watchdog

`tests/one-offs/watch_verify_failures.py` polls and freezes a full forensic snapshot the first time a **live** process fails verification (it deliberately ignores genuinely-dead processes, which are correct).

- [ ] `python tests/one-offs/watch_verify_failures.py 5` -> steady `ok` lines listing entry/process/`by_pid` counts.
- [ ] With the fix in place, launching an elevated session should NOT trigger it. Before the fix it fired within one poll.

## What the mocks don't cover

- **Real integrity levels.** The automated tests simulate the observed shape (name readable, cmdline empty); only a genuinely elevated process proves the OS behaves that way and that the fix meets it.
- **Claude Desktop actually running** alongside CLI sessions.
- Whether `via=` values in the log are *useful* to a human reading them under time pressure.
- Mixed populations: several sessions at different elevations at once, which is what produced the original confusing roster.

## Cross-platform note (untested, deliberately)

The mechanism is Windows-specific: `Name` and `CommandLine` are independent WMI fields, so one can survive when the other is withheld. On POSIX the enumeration derives the name **from the args themselves** (`args.split()[0]`), so if args are hidden there is no independent name to fall back to. Whether an equivalent blackout occurs on Linux (`hidepid`), macOS, or BSD is **unverified** -- a testable question, not a claim. Adding `comm=` to the `ps` format would supply an independent name if it turns out to be needed.
