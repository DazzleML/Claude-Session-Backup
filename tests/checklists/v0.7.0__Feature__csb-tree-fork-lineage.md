## What this is

`csb tree` renders the fork forest -- which Claude Code session spawned which -- as an indented CLI tree. This checklist covers what mocks cannot: real console rendering (box-drawing vs codepage), real vault topologies at real depth, the feel of the default view, and the upgrade path for an existing index.

## Prerequisites

1. csb v0.7.0 installed from this tree (`pip install -e ".[dev]"`), or run as `python -m claude_session_backup`.
2. **Lineage requires one indexing pass.** After upgrading, run `csb backup` (or `csb backup --no-commit`) once so existing sessions get their fork pointers extracted. Until then `csb tree` legitimately reports nothing.
3. **Safe rehearsal (recommended):** every step below is read-only except the indexing in step 2. To avoid touching your real index entirely, add `--db "%TEMP%\tree-test.db"` (PowerShell: `$env:TEMP\tree-test.db`; POSIX: `/tmp/tree-test.db`) to *both* the backup and every `csb tree` command.
4. You need at least one forked session for interesting output. If you have never forked, create one: resume any session with `claude --fork-session -r <uuid>`, send one message, exit, then re-run the backup.

**Reset between sections:** none needed -- `csb tree` and `csb show` are read-only.

## High-Value Verification (~5 minutes)

### HV.1 -- The forest renders, and singletons do not bury it

- [ ] **Steps:** `csb tree`
- [ ] **Expected:** Indented trees with `├──`/`└──` connectors (or `+--`/`\--` on a legacy console). Sessions that never forked do **not** each render as a one-node tree; they collapse into the footer, e.g. `9 trees | 41 sessions | 96 never forked (--orphans to list)`.
- [ ] **Why this matters:** The collapse is what makes the default view readable; without it the real chains drown in singletons.

### HV.2 -- A filter shows a session's ancestors AND descendants

- [ ] **Steps:** pick a name fragment from a forked session, then `csb tree <fragment>`
- [ ] **Expected:** The whole family renders -- ancestors above the match, descendants below, siblings alongside -- with matched nodes marked `*`. Exit 0.
- [ ] **Why this matters:** This is the core question the command exists to answer ("where did this session come from, and what came out of it?").

### HV.3 -- FILTER + PATH in one command

- [ ] **Steps:** `csb tree <fragment> "<a folder you have worked in>"`
- [ ] **Expected:** Only families where some session worked under that folder. A **non-path** second positional (e.g. `csb tree foo bar`) instead errors clearly and names `-d` -- it does not silently scope to nothing.
- [ ] **Why this matters:** The combined `list` + `scan` grammar is the headline ergonomic; the guard is what keeps a typo from silently returning an empty forest.

### HV.4 -- Purged ancestors keep chains intact

- [ ] **Steps:** `csb tree` and look for dimmed rows marked `[purged]`; then `csb tree --deleted all`
- [ ] **Expected:** By default, purged sessions appear **only** where they connect an in-scope chain (dimmed, `[purged]`); purged leaves are absent. `--deleted all` renders everything normally.
- [ ] **Why this matters:** This is the three-tier rule -- parity with `csb list` on scope, without ever showing a decapitated chain.

### HV.5 -- `csb show` reports lineage

- [ ] **Steps:** `csb show <uuid of a mid-chain session>`
- [ ] **Expected:** `Forked from:` and/or `Forks:` lines with names and fork dates, plus a `csb tree --root <id>` pointer. A session with no lineage shows **no** such block.
- [ ] **Why this matters:** The per-session view must agree with the forest, and unaffected sessions must look untouched.

### HV.6 -- Console rendering is correct for YOUR terminal

- [ ] **Steps:** run `csb tree` in cmd.exe, PowerShell, and (if available) Windows Terminal / a POSIX shell. Then `csb tree --ascii`, and `csb tree | more` (piped).
- [ ] **Expected:** No mojibake, no `UnicodeEncodeError`, no broken vertical rails. `--ascii` always renders `+--`/`\--`/`|`. Piped output stays aligned.
- [ ] **Why this matters:** Box-drawing is exactly where Windows codepages bite; automated tests cannot see your console.

## Section 1: selection and scoping

### 1.1 Filter modes

- [ ] `csb tree <substring>` -- matches name / project / UUID / folder paths
- [ ] `csb tree "<prefix>*"` -- anchored prefix; verify a session that merely *contains* the text is excluded
- [ ] `csb tree -E "^<regex>"` -- regex; and `csb tree -E "([unclosed"` errors cleanly (exit 2, no traceback)
- [ ] `csb tree <8-char-uuid-prefix>` -- UUID vocabulary works without a special flag

### 1.2 Component vs lineage

- [ ] `csb tree <fragment>` vs `csb tree <fragment> --lineage` -- the second shows fewer nodes (cousins dropped, the match's own line of descent kept). Compare the footer counts.

### 1.3 Root, orphans, scope

- [ ] `csb tree --root <uuid-prefix>` -- exactly one family; accepts a prefix/suffix like `csb show`
- [ ] `csb tree --orphans` -- only sessions that never forked
- [ ] `csb tree -D <folder>` vs `-d <folder>` -- folder-only vs folder+descendants
- [ ] `csb tree --deleted only` -- flips the population to purged sessions

## Section 2: display

### 2.1 Info levels (compare against `csb list`)

- [ ] `csb tree -f` adds `started:` + purge countdown per node
- [ ] `csb tree -ff` additionally adds `start at:`, other folders, and `N messages | vX.Y.Z`
- [ ] The wording/format of those lines matches what `csb list -f` / `-ff` print for the same session
- [ ] `--top 1` and `--all-folders` change the folder count under `-ff`

### 2.2 Identity and ordering

- [ ] `csb tree --shortid` -- compact `<head>-...-<tail>` UUIDs; default shows full UUIDs (paste-ready)
- [ ] `csb tree --sort messages` / `--sort size` / `--sort oldest` -- root order changes; **children always stay in fork order** (check a family with 2+ siblings against their `forked` dates)
- [ ] `csb tree -n 2` -- at most 2 families

### 2.3 Truncation and diagnostics

- [ ] `csb tree --max-nodes 5` -- a large family collapses with `... (N more -- csb tree --root <uuid>)`; following that hint shows the full family
- [ ] If you have a parent csb never indexed, it renders as `(unknown session) [not indexed]` with a stderr note about `csb update backfill-deleted`

## Section 3: machine output

- [ ] `csb tree --json` is valid JSON (`csb tree --json | python -m json.tool`), nested via `children`, with `session_id` / `in_scope` / `matched` per node
- [ ] Diagnostics (phantom-parent note, cycle warning) go to **stderr** and never pollute the JSON on stdout: `csb tree --json 2>/dev/null | python -m json.tool` still parses

## Section 4: upgrade path

- [ ] On a pre-v0.7.0 index, `csb tree` before re-indexing prints the "no lineage found" note that names `csb update rebuild-index`
- [ ] After `csb backup`, lineage appears -- and `csb status` / `csb list` behave exactly as before (the migration is additive)
- [ ] `csb update backfill-deleted` still runs; purged ancestors recovered from git also gain lineage

## What the automated tests DON'T cover

- **Your console.** Codepage behavior, font glyph coverage, rail alignment at your width, and color rendering are all environment-specific. cp1252 (PowerShell default) cannot encode box characters while cp437 (classic DOS) can -- only a real run proves which path yours takes.
- **Real vault topology and scale.** Fixtures use small synthetic forests; a real vault has deep chains, many singletons, and purged ancestors in combinations no fixture anticipates. Performance feel on a large index is likewise unmeasured here.
- **Whether the default view is the *right* view.** Is collapsing never-forked sessions into a footer count the behavior you want? Does the component view (siblings shown) beat `--lineage` as the default? Only using it answers that.
- **Cross-shell quoting** of `"NAME*"` and regex arguments (cmd.exe vs PowerShell vs bash differ on `*` and `^`).
- **The upgrade moment** on a large real index: how long the re-index takes, and whether the "run backup first" guidance is discoverable enough.
