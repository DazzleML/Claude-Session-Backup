# Human Test Checklist: plugin drift reads the authoritative version

**Target version:** v0.9.11
**Ships with commit:** TBD (pre-commit)
**Companion automated tests:** 24 in `tests/test_setup_update.py` (up from 14), plus fixture corrections in `tests/test_commands.py`. Suite: 1922 passed, 1 skipped. Of the new/changed tests, **9 are red-green anchors** (fail without the production change) and **5 are invariant guards** (pass either way).

## What this is

v0.9.5 shipped plugin drift detection. It compared the plugin version against the CLI's own version and, when they matched, printed the word **current** -- a claim about the world, from evidence only about itself. It also read the plugin version from the wrong place, and offered the same remedy for both directions of drift.

This checklist verifies the three corrections a human can see but mocks cannot: that the version reported is the one Claude Code actually loads, that each drift direction names the remedy that fixes it, and that no surface claims currency it never checked.

**What this release does NOT do:** it still never asks whether a newer csb exists. A machine whose plugin and CLI agree is reported as consistent, which is all that is provable. Upstream currency checking is separate work.

## Prerequisites

1. csb v0.9.11 installed (`csb -V`).
2. Python 3.10+ on PATH (used to build scratch fixtures cross-platform).
3. **Isolation**: every test below runs against a throwaway `--claude-dir`. Nothing writes to your real `~/.claude`, except the clearly-marked Section 5, which is read-only.

Set the scratch dir:

**cmd.exe**:
```cmd
set CSBTEST=%TEMP%\csb-drift-check
rmdir /s /q "%CSBTEST%" 2>nul
mkdir "%CSBTEST%"
```

**PowerShell**:
```powershell
$env:CSBTEST = "$env:TEMP\csb-drift-check"
if (Test-Path $env:CSBTEST) { Remove-Item -Recurse -Force $env:CSBTEST }
New-Item -ItemType Directory -Force $env:CSBTEST | Out-Null
```

**POSIX**:
```bash
export CSBTEST=/tmp/csb-drift-check
rm -rf "$CSBTEST" && mkdir -p "$CSBTEST"
```

### The fixture helper

This one-liner works in **all three shells** (outer double quotes, inner single quotes). It writes Claude Code's two registries into the scratch dir. Replace `0.9.9` with whatever version the step calls for; pass `NONE` to omit the recorded version entirely.

```
python -c "import json,os,pathlib,sys; v=sys.argv[1]; d=pathlib.Path(os.environ['CSBTEST'])/'plugins'; d.mkdir(parents=True,exist_ok=True); rec={'scope':'user'}; rec.update({} if v=='NONE' else {'version':v}); d.joinpath('known_marketplaces.json').write_text(json.dumps({'dazzle-claude-session-backup':{'source':{'repo':'DazzleML/Claude-Session-Backup'}}})); d.joinpath('installed_plugins.json').write_text(json.dumps({'version':2,'plugins':{'claude-session-backup@dazzle-claude-session-backup':[rec]}})); print('registry ->', v)" 0.9.9
```

### Seeding cache directories

```
python -c "import os,pathlib,sys; b=pathlib.Path(os.environ['CSBTEST'])/'plugins'/'cache'/'dazzle-claude-session-backup'/'claude-session-backup'; [ (b/x).mkdir(parents=True,exist_ok=True) for x in sys.argv[1:] ]; print('cached ->', sys.argv[1:])" 0.9.9 0.9.10
```

### Reset between sections

Re-run the scratch-dir creation block above. Every section is independent.

## High-Value Verification (~5 minutes)

### HV.1 -- The false green is gone

Validates: the version reported is the one Claude Code **loads**, not the newest one merely downloaded.

- [ ] **Steps:**
  1. Reset the scratch dir.
  2. Seed cache dirs `0.9.9` and a version NEWER than your csb (e.g. `99.0.0`).
  3. Write the registry with version `0.9.9`.
  4. `csb status --claude-dir "%CSBTEST%"` (PowerShell: `$env:CSBTEST`; POSIX: `"$CSBTEST"`)
- [ ] **Expected:** the `Plugin:` line names **0.9.9**, not 99.0.0, and reports drift.
- [ ] **Why this matters:** the cache keeps every version ever fetched and prunes none (8 on the author's machine). If csb reports the newest *directory*, it will call a stale install current while the old hook scripts keep firing.

### HV.2 -- `csb status` no longer claims currency

Validates: the wording claims only what the filesystem proves.

- [ ] **Steps:**
  1. Reset. Write the registry with **your own csb version** (`csb -V` shows it).
  2. `csb status --claude-dir <scratch>`
- [ ] **Expected:** the Plugin line reads `<version> (matches CLI)`. The word **current** appears nowhere.
- [ ] **Why this matters:** "current" asserts agreement with what exists upstream. Nothing on this path looked upstream, so the word was never earned.

### HV.3 -- Drift has two directions

Validates: when the CLI is the stale half, csb says so.

- [ ] **Steps:**
  1. Reset. Write the registry with version `99.0.0`.
  2. `csb setup --claude-dir <scratch> --auto`
- [ ] **Expected:** the `auto-backup plugin` row is `[ ]`, names both versions, and its command line is **`pip install -U claude-session-backup`** -- NOT `csb setup update`.
- [ ] **Why this matters:** recommending a plugin update here is a closed loop -- the update finds nothing, exits 0, and the row stays unticked forever.

### HV.4 -- `csb setup update` refuses a pointless update

- [ ] **Steps:** with the registry still at `99.0.0`: `csb setup update --claude-dir <scratch>`
- [ ] **Expected:** exit code **3**, a message saying the plugin is already ahead of this csb, and the `pip install -U` remedy on stderr. The `claude` CLI is **not** invoked.
- [ ] **Check:** `echo %ERRORLEVEL%` (cmd) / `$LASTEXITCODE` (PowerShell) / `echo $?` (POSIX)
- [ ] **Why this matters:** this is the loop's other exit. Even if the checklist row is right, a user who runs the suggested command must not get "already current" and a clean exit.

### HV.5 -- An unrankable pair names no remedy

- [ ] **Steps:** reset; write the registry with version `0.9.10b1`; `csb setup --claude-dir <scratch> --auto`
- [ ] **Expected:** the row is `[ ]` and names both versions, but prints **neither** `csb setup update` nor `pip install -U`.
- [ ] **Why this matters:** "these differ" is provable; "yours is older" is not. Guessing a direction here would send someone the wrong way.

## Section 1: Detection sources and fallbacks (~5 min)

### 1.1 Registry wins over cache

- [ ] Reset; cache `0.9.9` + `99.0.0`; registry `0.9.9`.
- [ ] `csb status --claude-dir <scratch>` -> reports `0.9.9`.

### 1.2 No registry -> cache fallback still works

- [ ] Reset; seed cache `0.8.4` only; do **not** write registries.
- [ ] `csb status --claude-dir <scratch>` -> Plugin line reports `0.8.4 installed`.
- [ ] **Check:** the fallback was retained, not replaced -- a missing registry must not blind detection.

### 1.3 Malformed registry -> cache fallback, no crash

- [ ] Reset; seed cache `0.8.4`; then corrupt the registry:
  ```
  python -c "import os,pathlib; p=pathlib.Path(os.environ['CSBTEST'])/'plugins'/'installed_plugins.json'; p.parent.mkdir(parents=True,exist_ok=True); p.write_bytes(b'{ not json')"
  ```
- [ ] `csb status --claude-dir <scratch>` -> exits 0, reports `0.8.4`, prints no traceback.

### 1.4 Registry with a BOM is still read

- [ ] Reset; write a BOM-prefixed registry:
  ```
  python -c "import json,os,pathlib; p=pathlib.Path(os.environ['CSBTEST'])/'plugins'/'installed_plugins.json'; p.parent.mkdir(parents=True,exist_ok=True); p.write_bytes(b'\xef\xbb\xbf'+json.dumps({'version':2,'plugins':{'claude-session-backup@dazzle-claude-session-backup':[{'version':'0.9.9'}]}}).encode())"
  ```
- [ ] `csb status --claude-dir <scratch>` -> reports `0.9.9`.
- [ ] **Why:** PowerShell 5.1 `Set-Content` writes BOMs; a rejected registry would read as "not installed" and re-instruct an already-done step.

### 1.5 Neither source knows -> stay quiet

- [ ] Reset; write registry with `NONE` (no version field); no cache dirs.
- [ ] `csb setup --claude-dir <scratch> --auto` -> `auto-backup plugin` row is `[x]`, no drift, no command line.
- [ ] **Why:** when nothing can answer, csb must not invent a drift.

## Section 2: Both surfaces agree (~3 min)

### 2.1 Same verdict from `csb status` and `csb setup`

- [ ] For each of these registry versions -- `0.8.4` (behind), your own version (match), `99.0.0` (ahead) -- run **both** `csb status` and `csb setup --auto` against the scratch dir.
- [ ] **Expected:** the two surfaces never disagree about the direction or the remedy.
- [ ] **Eyeball check:** the status line is yellow for drift, green for match, dim for absent. Colors should read as "attention / fine / not applicable" at a glance.

## Section 3: `csb setup update` exit codes (~5 min)

> Skip 3.3 if you don't want to touch your real plugin install.

### 3.1 Not installed

- [ ] Reset (empty scratch dir); `csb setup update --claude-dir <scratch>`
- [ ] **Expected:** exit **3**; stderr shows both the `marketplace add` and `plugin install` commands.

### 3.2 Plugin ahead of the CLI

- [ ] Registry `99.0.0`; `csb setup update --claude-dir <scratch>`
- [ ] **Expected:** exit **3**; "already ahead of this csb"; `pip install -U` on stderr; `claude` never invoked.

### 3.3 A clean update that lands nothing (real `claude` CLI)

- [ ] On a machine where the plugin genuinely trails the CLI **and** the marketplace has nothing newer, run `csb setup update`.
- [ ] **Expected:** exit **1**, `No change: still <v>, and csb is <v>`, and stderr naming the marketplace refresh (`claude plugin marketplace add "..."`) then `csb setup update`.
- [ ] **What changed:** this used to print `Already current` and exit **0** while the checklist row stayed `[ ]` -- a reassuring word with no way forward.
- [ ] **Note:** hard to stage deliberately; if you can't reach this state, mark N/A rather than faking it.

## Section 4: Degradation and error quality (~3 min)

### 4.1 No plugin at all is calm, not a warning

- [ ] Empty scratch dir; `csb status --claude-dir <scratch>`
- [ ] **Expected:** `not installed (optional -- hook automation off)`, dim. CLI-only users are first-class; this must not read as an error.

### 4.2 Error message quality (judgement call)

- [ ] Read the three drift messages aloud. Does each one tell you **what is wrong** and **exactly what to type**?
- [ ] Is it obvious which of the two versions is yours? (`0.9.9 installed -- csb is 0.9.10`)
- [ ] **Finding if:** you have to think about which half is stale.

## Section 5: Your real machine (read-only) (~2 min)

> These commands read your real `~/.claude`. They write nothing.

### 5.1 The live repro

- [ ] `csb setup` (no `--claude-dir`)
- [ ] **Expected:** if your installed plugin trails your CLI, the row is `[ ]` with both versions named. If they match, `[x]`.
- [ ] **Cross-check:** compare against Claude Code's own record:
  ```
  python -c "import json,os,pathlib; p=pathlib.Path(os.path.expanduser('~'))/'.claude'/'plugins'/'installed_plugins.json'; d=json.loads(p.read_text(encoding='utf-8-sig')); print([r.get('version') for r in d['plugins'].get('claude-session-backup@dazzle-claude-session-backup',[])])"
  ```
- [ ] **Expected:** the version csb reports **equals** the version printed here. If they differ, that is the bug this release fixes and it is not fixed.

### 5.2 Cache accumulation (informational)

- [ ] List your plugin cache:
  ```
  python -c "import os,pathlib; b=pathlib.Path(os.path.expanduser('~'))/'.claude'/'plugins'/'cache'/'dazzle-claude-session-backup'/'claude-session-backup'; print(sorted(x.name for x in b.iterdir()) if b.exists() else 'none')"
  ```
- [ ] **Observe:** likely several versions, none pruned. This is why 5.1's cross-check matters -- the newest directory is not necessarily the running one.

## What the automated tests DON'T cover

- **Real `claude plugin update`** -- every wrapper test mocks `subprocess.run`. Section 3.3 is the only place the real CLI runs, and its "nothing to fetch" state is hard to stage.
- **Terminal colour rendering** -- the yellow/green/dim distinction is asserted only as a style argument, never as a rendered result. Section 2.1's eyeball check is the only real verification.
- **Real Claude Code registry shapes** -- fixtures are hand-built. If Claude Code changes `installed_plugins.json`'s schema (e.g. multiple scopes for one plugin, or a project-scoped entry alongside a user one), only Section 5.1 catches it.
- **Multi-scope installs** -- the code returns the first record carrying a version. A machine with both a user-scope and project-scope install of the same plugin is untested.
- **Windows codepage** -- messages are ASCII, but no test renders them through cmd.exe at codepage 437.
- **Whether the reported version is the one whose hooks actually fired** -- csb trusts Claude Code's registry. Nothing verifies that claim against a running hook.
