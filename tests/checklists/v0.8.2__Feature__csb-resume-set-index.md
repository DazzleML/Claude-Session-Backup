## What this is

The roster numbers from v0.8.0/v0.8.1 become addresses: `csb resume set 3` reclaims member 3. This checklist covers what mocks cannot -- a real `claude` launch in a real terminal, the actual reclaim loop across several windows, and the one thing the whole design turns on: **csb must never open a window of its own.**

## Prerequisites

1. csb v0.8.2 installed from this tree (`pip install -e ".[dev]"`).
2. A machine that has restarted at least once, so `csb set show last` has a roster.
3. **These steps launch real Claude Code sessions.** Nothing is destructive, but you will end up with sessions open -- close them when done.

**Reset between sections:** none needed; every step is a launch, not a mutation.

## High-Value Verification (~10 minutes)

### HV.1 -- csb never opens a window

- [ ] **Steps:** in a terminal, `csb set show last`, then `csb resume set 1`
- [ ] **Expected:** the session opens **in that same terminal**. No new window. No new tab. No console flash.
- [ ] **Why this matters:** this is the design's central promise. Automated tests assert no `Popen`/`os.system`/`startfile` call, but only your eyes confirm nothing appeared on screen.

### HV.2 -- The reclaim loop across several windows

- [ ] **Steps:** open 3 terminals of your own choosing (mix `cmd.exe`, PowerShell, Windows Terminal if you like). In each, position it where you want, then run `csb resume set 1`, `csb resume set 2`, `csb resume set 3`.
- [ ] **Expected:** three sessions, each in the terminal *you* chose and placed. The arrangement is yours; csb only supplied the addressing.
- [ ] **Why this matters:** this is the whole feature in one exercise -- and the reason `csb set resume` (spawn-them-all) was deliberately not built.

### HV.3 -- The number means what the roster said

- [ ] **Steps:** `csb set show last`, note the name at row 3. Then `csb resume set 3` and check the session that opens.
- [ ] **Expected:** the same session. Then run `csb set show last --window 24` (a narrower view, likely fewer rows) and `csb resume set 3` again -- **still the same session.**
- [ ] **Why this matters:** the stable-number guarantee. A narrowed view must never renumber what an index addresses.

### HV.4 -- Duplicate names, where the index earns its keep

- [ ] **Steps:** if your roster has two rows with the same session name (`csb set show last` -- check), try the row's own hint `csb resume <that name>`, then try `csb resume set <its number>`.
- [ ] **Expected:** the name is ambiguous (error or the wrong session); the number resolves exactly.
- [ ] **Why this matters:** this is the concrete case where names fail and indices do not -- and it is real on any vault with branch-per-topic naming.

### HV.5 -- Forking a member

- [ ] **Steps:** `csb resume set 2 -- --fork-session`
- [ ] **Expected:** a *new* session branched from member 2, not a resume of it. Afterwards `csb tree` shows the fork under its parent.
- [ ] **Why this matters:** the passthrough is what makes the roster a launchpad for `/branch`-style work, and it closes the loop with fork lineage.

## Section 1: the selector forms

- [ ] `csb resume set 2` -- member 2 of the last epoch
- [ ] `csb resume set last 2` -- identical result to the above
- [ ] `csb set new CSB-STACK <a> <b>` then `csb resume set CSB-STACK 2` -- member 2 of the named set (insertion order, not activity order)
- [ ] `csb resume <name>` -- the plain form still works exactly as before

## Section 2: errors name the way out

- [ ] `csb resume set` (bare) -- exit 2, asks which member, points at `csb set show last`, and mentions the UUID route for a session literally named `set`
- [ ] `csb resume set 99` -- exit 1, names the valid range (e.g. `1-8`)
- [ ] `csb resume set 0` -- exit 2, "roster numbers start at 1"
- [ ] `csb resume set CSB-STACK` (name, no number) -- exit 2, "not a roster number"
- [ ] `csb resume set NO-SUCH-SET 1` -- exit 1, "No set named"
- [ ] `csb resume <name> extra-arg` -- exit 2, explains the `--` route for claude flags
- [ ] None of the above launches anything

## Section 3: edge cases

- [ ] A **purged** member: `csb resume set <its N>` walks the restore-from-git prompt, then resumes (same flow as `csb resume` on a pruned session)
- [ ] A set with a member no longer in the index at all -- clear error naming `csb update rebuild-index`, no launch attempt
- [ ] An empty named set -- "has no members", no launch
- [ ] On a machine with no shutdown fence in the log: `csb resume set 1` says so rather than erroring obscurely

## Section 4: the arrangement over time

- [ ] Reclaim two members, then re-run `csb set show last`. Note: sessions you have since resumed may **drop off** the roster, because membership is computed from `last_active_at`, which moves forward when you use a session.
- [ ] Judgment call: is that the right behavior? It reads as "what's left to reclaim" but the header claims "what was active before shutdown". This is the known limit of the activity heuristic -- the observation phase (#64) records immutable open/close events and fixes it. Record whether it bit you in practice.

## What the mocks don't cover (why this checklist exists)

- Whether a window actually appears (the central promise)
- The real reclaim loop across several terminal emulators
- Real `claude --resume` behavior, including forking a live session
- Whether the numbers feel like a usable interface after a real restart
- The roster-drift question in Section 4

## Cleanup

Close any sessions you opened. `csb set rm CSB-STACK` if you created a set for Section 1.
