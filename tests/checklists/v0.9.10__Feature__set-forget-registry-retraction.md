# v0.9.10 -- Feature -- `csb set forget`: retract a stale registry entry

Hand-runnable companion to `tests/test_set_current.py::TestSetForget` (7 tests). Verifies the verb that lets you testify about what csb cannot know -- and, more importantly, verifies that it **refuses** to let you assert something csb can see is false.

**Legend** (for external testers): "the registry" = `csb-live/` under your Claude data dir, one JSON entry per open session; "retract" = remove an entry because you know the session is closed; "verifiably running" = csb found a live process whose identity matches the entry's recorded pid.

## Why the verb exists

A session closed with **Ctrl+C** leaves its entry behind: Claude Code cancels the SessionEnd hook before it can erase it. An entry written by an older plugin carries no host pid, so nothing can resolve it either way. Both read `[no exit observed]` indefinitely -- indistinguishable from genuine crash evidence, which is the one ambiguity the tier ladder exists to avoid. You were there; csb was not.

## Prerequisites

- csb at the version carrying this checklist (`csb -V`).
- At least one session open (for the refusal check) and ideally one stale entry.

**To create a stale entry deliberately**: start a scratch session (`claude` in any folder), then close it with **Ctrl+C** rather than `/exit`. It should linger in `csb set current` as `[no exit observed]`.

## 1. The refusal (the load-bearing check)

- [ ] `csb set current` -> note a row that is genuinely `[running]`.
- [ ] `csb set forget current:<that row>` -> **refuses**, exit 1, naming the session and pointing at `--force`.
- [ ] `csb set current` again -> that session is still listed. Nothing was removed.

This is the important half: the verb's job is as much to *stop* a wrong assertion as to record a right one.

## 2. Retracting a genuinely stale entry

- [ ] With a Ctrl+C'd session showing `[no exit observed]`: `csb set forget current:<its row>`
- [ ] Output confirms `Retracted <short-uuid>` with its start time and folder.
- [ ] A note follows: the entry remains in your backup store's history (`git log -- csb-live/`).
- [ ] `csb set current` -> the row is gone, and the session count dropped by one.

## 3. It is recoverable, and the note is true

- [ ] `git -C <claude-dir> log --oneline -- csb-live/ | head -5` -> commits touching the registry exist.
- [ ] `git -C <claude-dir> log -p -- csb-live/<uuid>.json | head -30` -> the retracted entry's content is visible in history.
      (If nothing shows, the entry was created and retracted between two backups and was never committed -- worth knowing, and not a bug in this verb.)

## 4. A row with no entry behind it errors

- [ ] `csb set show last` -> pick any row (epoch rows come from the index, not the registry).
- [ ] `csb set forget last:<N>` -> exit 1, saying there is no live-registry entry and that an index-derived row is not an observation.
- [ ] This should NOT silently succeed: the row will still be there next invocation, and a silent success would hide that.

## 5. `--force`, and what it is for

- [ ] `csb set forget current:<a running row> --force` -> retracts it despite the session running.
- [ ] `csb set current` -> that session vanishes from the roster **even though it is still running**.
- [ ] Understand what you just did: `--force` is for *privacy* (an entry recording a path you would rather not keep), not for asserting a false state. The session will re-register on its next hook fire.
- [ ] Recover: let the session fire any hook (send it a message), then `csb set current` -> it returns.

## 6. Ordinary vocabulary still works

- [ ] `csb set forget <session-name>` and `csb set forget <uuid-prefix>` resolve the same way every other csb command does.
- [ ] `csb set forget` with no argument -> exit 2, teaching both forms.
- [ ] `csb set rm current` -> still errors with "No set named 'current'". `rm` edits membership you declared; `forget` retracts evidence csb recorded. They are deliberately different verbs.

## What the mocks don't cover

- A **real** Ctrl+C-orphaned entry, produced by Claude Code actually cancelling the hook -- the automated tests construct the end state directly.
- Whether the refusal message is persuasive in the moment: if you find yourself reaching for `--force` reflexively, the wording is too weak and that is a finding.
- The git-history claim in section 3 against a real backup store.
- Whether `forget` reads as obviously distinct from `rm` to someone who did not read this file (the naming decision is recorded as RV1; contrary experience is worth hearing).

## Cleanup

Any scratch session from the prerequisites: close it normally (`/exit`) so its entry is erased cleanly. If you used `--force` on a live session in section 5, send that session a message to re-register it.
