## What this is

A **named set** is a curated group of sessions -- the windows that go with one task, or a standing working set. Unlike a boot epoch (observed automatically), a named set is something you declare. This checklist covers what mocks cannot: the file's real interaction with your backup store's git history, recovery from a genuinely corrupt file, and whether the naming conventions feel right in daily use.

## Prerequisites

1. csb v0.8.1 installed from this tree (`pip install -e ".[dev]"`), or run as `python -m claude_session_backup`.
2. A backup store with git (`csb status` shows the repo) -- Section 2 needs real commits.
3. **Rehearsal option:** every step except Section 2 works against `--claude-dir <temp> --db <temp>`. Section 2 deliberately uses your real store, but only *adds* a set you then delete.

**Reset between sections:** `csb set rm <name>` removes anything you create. The sets file itself is git-tracked, so `git checkout csb-sets.json` in the store restores any prior state.

## High-Value Verification (~5 minutes)

### HV.1 -- Create a set that spans projects

- [ ] **Steps:** pick two sessions from *different* projects, then `csb set new CSB-STACK <session-a> <session-b>` and `csb set show CSB-STACK`
- [ ] **Expected:** both members listed, numbered 1 and 2, each with its own `start at:` folder and a paste-able `csb resume` line. The roster looks identical in shape to `csb set show last`.
- [ ] **Why this matters:** spanning projects is the case the naming convention is designed around, and shared rendering is an explicit AC.

### HV.2 -- The set is really in git

- [ ] **Steps:** `csb backup`, then in your backup store: `git log --oneline -1 -- csb-sets.json` and `git show --stat HEAD | head`
- [ ] **Expected:** `csb-sets.json` appears in a commit whose message is the **user** sync message (configs/skills/logs), not the noise one.
- [ ] **Why this matters:** the whole survives-a-rebuild claim rests on the file being backed up in the right class. Automated tests assert the list membership; only a real store proves the commit.

### HV.3 -- Rebuild the index, set survives

- [ ] **Steps:** `csb update rebuild-index`, then `csb set show CSB-STACK`
- [ ] **Expected:** unchanged. Members still resolve, numbering unchanged.
- [ ] **Why this matters:** this is the failure mode the storage decision exists to prevent.

### HV.4 -- Reserved names are refused, near-misses are not

- [ ] **Steps:** `csb set new last x`, `csb set new 42 x`, then `csb set new last-one <session>`
- [ ] **Expected:** the first two exit 2 with a message naming the reason; the third succeeds. (Delete it after: `csb set rm last-one`.)
- [ ] **Why this matters:** over-refusing would be worse than under-refusing -- csb should not be the tool that tells you your name is wrong.

## Section 1: CRUD behavior

- [ ] `csb set add CSB-STACK <a-third-session>` -- reports "Added 1 session"
- [ ] Run that exact command again -- reports "already a member", exit 0, membership unchanged
- [ ] `csb set rm CSB-STACK <a-session-that-is-not-a-member>` -- "not a member", exit 0, nothing removed
- [ ] `csb set add NOPE <session>` and `csb set rm NOPE` -- exit 1 with a message naming `csb set new` / `csb set list`
- [ ] `csb set new CSB-STACK <session>` (duplicate name) -- refused, points at `csb set add`
- [ ] `csb set new MIXED <good-session> <deliberate-typo>` -- **the whole create aborts**; `csb set list` shows no `MIXED`. (A half-built set would be worse than none.)
- [ ] Case-insensitivity: `csb set show csb-stack` finds `CSB-STACK`

## Section 2: file, git, and recovery

- [ ] `csb set list` after several creates -- counts and "updated" dates look right
- [ ] Open `csb-sets.json` in the store: readable, sorted keys, one member entry per session with `session_id` + `added_at`
- [ ] **Corruption refusal:** back up the file, then append a stray `{` to it and run `csb set list`. Expect a clear error naming the file **and** the git remedy -- and confirm the corrupt content is still on disk (nothing silently reset it). Restore with `git checkout csb-sets.json`.
- [ ] **Hand-edited reserved name:** add a `"last": {"members": []}` entry by hand, run `csb set list`. Expect a warning on stderr and the entry ignored -- `csb set show last` must still be the boot epoch, not your set.
- [ ] **Recovery:** `csb set rm <name>` a real set, then `git checkout csb-sets.json` in the store and confirm `csb set show <name>` works again.

## Section 3: display and edge cases

- [ ] A set containing a **purged** session -- shows the purge marker, and its resume hint still offers restore
- [ ] A set containing a session no longer in the index at all -- shows `[not in index]`, keeps its number, and a footer note explains. It must NOT vanish from the list.
- [ ] `csb set new EMPTY-ISH <session>` then `csb set rm EMPTY-ISH <that same session>` -- the now-empty set reports "no members" rather than rendering nothing
- [ ] `csb set show CSB-STACK --json | python -m json.tool` -- parses; `kind` is `named`, `epoch` is null, members numbered from 1
- [ ] `csb set list --json` -- parses; counts match the human output
- [ ] Narrow terminal (~80 cols) and cmd.exe: names with non-ASCII render without errors

## Section 4: naming conventions in practice

- [ ] Create one **standing** set (`CSB-STACK`) and one **snapshot** set (`2026-8-3__something`). Do both read clearly in `csb set list` a day later?
- [ ] Does the two-shape rule in `docs/naming.md` match what you actually reach for, or does daily use suggest a third shape?
- [ ] Judgment call: is `csb set` the right verb, or does anything read awkwardly in practice now that all five actions exist?

## What the mocks don't cover (why this checklist exists)

- Real git history interaction -- which commit class, and whether recovery actually works
- A genuinely corrupt file (tests simulate one; a real one may fail differently)
- Whether the naming conventions survive contact with real use
- The feel of the CRUD grammar across five actions

## Cleanup

```bash
csb set list                 # see what you created
csb set rm CSB-STACK         # ...and remove each
csb set rm last-one
```
The sets file is git-tracked, so `git checkout csb-sets.json` in the backup store returns it to its pre-checklist state.
