# Human Test Checklist: Scheduled Backup (`csb setup schedule`, #69)

**Target version:** 0.9.0
**Ships with commit:** v0.9.0: feat: scheduled backup -- csb setup schedule (#69), branch `issue-69-scheduled-backup`
**Companion automated tests:** 140 tests across `tests/test_schedule.py` (47, incl. golden files in `tests/fixtures/schedule/`), `tests/test_schedule_backends.py` (38), `tests/test_setup_schedule.py` (33), `tests/test_schedule_evidence.py` (14), `tests/test_backup_runlog.py` (8)

## What this is

Hand-runnable verification for the scheduled-backup feature: `csb setup schedule` registering a recurring `csb backup` with the OS scheduler (Windows Task Scheduler / cron / launchd). The automated suite mocks every OS boundary (`schtasks`, `crontab`, `launchctl`, the backend seam), which is exactly why this document exists: only a human (or a container) can prove the *real* scheduler accepts the entry, actually fires it, and that the evidence trail tells the truth. Run it before releasing the feature and after any change to `schedule.py`, `schedule_backends.py`, or the setup wiring.

## Legend

- **Prime run** — the immediate first run install triggers through the scheduler's own launcher, so environment problems surface at install time.
- **Evidence verdict** — the `--status` conclusion combining OS readback + csb's run log (`csb-logs/schedule.log`): `ok`, `pending`, `not-installed`, or `INSTALLED BUT NOT RUNNING`.
- **Per-release re-verification** — Section 6: assumptions about Claude Code's own purge behavior that must be re-checked when Claude Code updates, not once.

## Prerequisites

1. **HARD BLOCKER — this branch MUST be the pip-installed package, not just your cwd.** The scheduled entry runs `pythonw -m claude_session_backup` with no working directory, so the OS scheduler resolves whatever package pip has installed — it can NOT be shadowed by running from a checkout the way your manual testing is. If pip points at another branch, every install below LOOKS green (dry-run, install message, even `csb -V` if your PATH differs) while the scheduled entry itself dies silently (observed: `Last Result: 2` from a main-branch install that predates `--log-file`). Before anything else:

   ```
   pip install -e ".[dev]"        (from this branch's checkout)
   csb -V                          -> must show this branch's dev build
   pip show claude-session-backup  -> Location/editable path must be this checkout
   ```

   Do not proceed until all three agree.
2. A throwaway backup store for data isolation — every command below passes `--claude-dir` at a scratch path:

   **cmd.exe**:
   ```cmd
   set CSB_TEST_DIR=%TEMP%\csb-sched-test
   mkdir %CSB_TEST_DIR%
   git -C %CSB_TEST_DIR% init
   ```

   **PowerShell**:
   ```powershell
   $env:CSB_TEST_DIR = "$env:TEMP\csb-sched-test"
   New-Item -ItemType Directory -Force $env:CSB_TEST_DIR
   git -C $env:CSB_TEST_DIR init
   ```

   **POSIX**:
   ```bash
   export CSB_TEST_DIR=/tmp/csb-sched-test
   mkdir -p "$CSB_TEST_DIR"
   git -C "$CSB_TEST_DIR" init
   ```

3. **CRITICAL — the scheduler itself is NOT isolated.** There is one Task Scheduler / crontab / LaunchAgents dir per user, and the entry name is fixed (`csb-scheduled-backup` / the fenced crontab block / `com.dazzleml.csb-backup`). Install steps below **replace any real csb schedule you already have** (a pre-mutate snapshot is taken under `backups/csb-schedule/` in whichever store the command targeted). If this machine has a production csb schedule, note its interval now (`csb setup schedule --status`) and re-install it against your real store in Cleanup.
4. Reset between sections: `csb setup schedule --remove --claude-dir <CSB_TEST_DIR>` and delete the scratch store.

## High-Value Verification (~10 minutes + one 2-minute wait)

**If you only have these minutes**, run these six. HV.4 is the single most load-bearing test in this document: it is the only one that proves a real scheduler daemon *delivers* the entry.

### HV.1 — Dry run renders, changes nothing

Validates: rendering, context freezing, and the no-mutation promise of `--dry-run`.

- [ ] **Steps** (cross-shell; substitute your shell's variable syntax for `<CSB_TEST_DIR>`):
  ```
  csb setup schedule --dry-run --interval 720 --claude-dir <CSB_TEST_DIR>
  csb setup schedule --status --claude-dir <CSB_TEST_DIR>
  ```
- [ ] **Expected:** the platform artifact prints (task XML on Windows / crontab block on Linux / plist on macOS); the `Command:` line shows an **absolute interpreter** (on Windows: `pythonw.exe`), `-m claude_session_backup`, `--claude-dir`, and `--log-file` — never a bare `csb`; "Nothing was installed (--dry-run)"; status still says not installed.
- [ ] **Why this matters:** the frozen-context command line is the entire defense against the entry silently dying in the scheduler's profile-less environment.

### HV.2 — Real install -> prime -> status -> remove (host OS)

Validates: the full lifecycle against the real scheduler.

- [ ] **Steps:**
  ```
  csb setup schedule --auto --interval 720 --claude-dir <CSB_TEST_DIR>
  csb setup schedule --status --claude-dir <CSB_TEST_DIR>      (wait ~30-60s after install first)
  csb setup schedule --remove --claude-dir <CSB_TEST_DIR>
  csb setup schedule --status --claude-dir <CSB_TEST_DIR>
  ```
- [ ] **Expected:** install reports the backend and cadence; prime run is dispatched; after the prime completes, `<CSB_TEST_DIR>/csb-logs/schedule.log` contains one `outcome=ok` line and status verdict is `ok`; remove reports removal; final status says not installed. **On Windows: no console window may flash at any point** (install, prime, or the scheduled run).
- [ ] **Why this matters:** this is the feature. If the OS rejects the entry or the prime leaves no evidence, nothing else here matters.

### HV.3 — Honest refusal where no cron daemon runs (Docker)

Validates: refusal-over-fake-success on minimal Linux.

- [ ] **Steps** (any cron-less image; most minimal images are):
  ```
  docker run --rm -v <repo>:/src python:3.12-slim sh -c "pip install -q /src && csb setup schedule --auto --claude-dir /tmp/s; echo rc=$?"
  ```
- [ ] **Expected:** the full refusal text (what was checked, per-distro install commands, the `--print-systemd` escape hatch), "Nothing was installed or modified.", **rc=11**.
- [ ] **Why this matters:** writing a crontab no daemon reads is the worst outcome this feature can produce — installed-looking, running never.

### HV.4 — Live fire through a real cron daemon (Docker, ~2 min)

Validates: real daemon *delivery* — not just spool acceptance. Uses `--interval 1` so the first real fire lands within 60s.

- [ ] **Steps:**
  ```
  docker run --rm -v <repo>:/src ubuntu:24.04 bash -c "
    apt-get update -qq && apt-get install -y -qq cron python3 python3-pip python3-venv git >/dev/null &&
    service cron start &&
    python3 -m venv /v && /v/bin/pip install -q /src &&
    mkdir -p /tmp/s && git -C /tmp/s init -q && git -C /tmp/s config user.email t@t && git -C /tmp/s config user.name t &&
    PATH=/v/bin:\$PATH /v/bin/csb setup schedule --auto --interval 1 --claude-dir /tmp/s &&
    sleep 90 && cat /tmp/s/csb-logs/schedule.log &&
    PATH=/v/bin:\$PATH /v/bin/csb setup schedule --status --claude-dir /tmp/s"
  ```
- [ ] **Expected:** the log shows the prime line **plus at least one later line written by cron itself** (distinct timestamp ~the next minute boundary); status verdict `ok`.
- [ ] **Why this matters:** the prime run proves the command; only a cron-originated line proves the daemon actually delivers it. This is the gap that let the prior-art scheduler rot undetected.

### HV.5 — The verdict this feature exists to say

Validates: `INSTALLED BUT NOT RUNNING` from stale evidence.

- [ ] **Steps:** with the entry installed (HV.2 state, before remove), edit `<CSB_TEST_DIR>/csb-logs/schedule.log` and rewrite its line's date to 4+ days ago (keep the format); run `csb setup schedule --status --claude-dir <CSB_TEST_DIR>` and `csb status --claude-dir <CSB_TEST_DIR>`.
- [ ] **Expected:** both surfaces say **INSTALLED BUT NOT RUNNING** with the age and expected cadence. Restore/delete the log after.
- [ ] **Why this matters:** a dead schedule that looks healthy is precisely what hand-rolled entries produce; this verdict is the differentiator.

### HV.6 — Ambient surfaces

Validates: `csb status` line + setup checklist row.

- [ ] **Steps:** with nothing installed: `csb status --claude-dir <CSB_TEST_DIR>`, then `csb setup --auto --claude-dir <CSB_TEST_DIR>`.
- [ ] **Expected:** status shows `Scheduled: no scheduled backup entry -- install with: csb setup schedule`; the setup checklist shows a yellow `[ ] scheduled backup` row with the exact command; after an install, both flip (`ok`/`[x]`).
- [ ] **Why this matters:** discoverability — users who never read the docs must still meet the feature.

## Section 1: Windows Task Scheduler (~10 min)

### 1.1 Task properties in the GUI

- [ ] **Steps:** install (HV.2), open Task Scheduler (`taskschd.msc`), find `csb-scheduled-backup`.
- [ ] **Check:** runs as the current user, **not** elevated ("Run only when user is logged on" semantics acceptable); Conditions tab: battery start allowed, no stop-on-battery; Settings tab: "Run task as soon as possible after a scheduled start is missed" checked; trigger cadence matches the chosen interval; action runs `pythonw.exe`, not `python.exe`.

### 1.2 Right-click "Run" produces evidence silently

- [ ] **Steps:** in the GUI, right-click the task -> Run. Watch the screen.
- [ ] **Expected:** no console window, no flash (including from git children); a new `outcome=ok` line in `schedule.log` within ~2 min.

### 1.3 Re-install is an idempotent overwrite with a snapshot

- [ ] **Steps:** install at `--interval 720`, then again at `--interval 1440`.
- [ ] **Expected:** second install succeeds (`/f` overwrite); a pre-install snapshot of the old task XML appears under `<CSB_TEST_DIR>/backups/csb-schedule/`; GUI shows the new cadence.

### 1.4 Legacy hand-rolled task detection

- [ ] **Steps:** create the old-doc task, install, observe, clean up:
  ```cmd
  schtasks /create /tn "Claude Session Backup" /tr "csb backup --quiet" /sc minute /mo 15
  csb setup schedule --auto --claude-dir %CSB_TEST_DIR%
  schtasks /delete /tn "Claude Session Backup" /f
  ```
- [ ] **Expected:** install output notes the legacy task and prints the exact `schtasks /delete` command; csb never deletes it itself.

### 1.5 Remove-nothing exits clean

- [ ] **Steps:** with nothing installed, `csb setup schedule --remove --claude-dir <CSB_TEST_DIR>`; check exit code (`echo %ERRORLEVEL%` / `echo $?`).
- [ ] **Expected:** "Nothing to remove", rc=0.

## Section 2: cron -- Linux / WSL / BSD (~15 min, Docker or WSL)

### 2.1 Marker-block surgery never touches user lines

- [ ] **Steps:** in a cron-capable environment, seed a crontab with a personal line (including one that *mentions* csb, e.g. `# my note: csb backup rocks` and `5 4 * * * /home/me/bin/csb-unrelated.sh`), install, `crontab -l`, remove, `crontab -l`.
- [ ] **Expected:** after install: personal lines byte-identical, plus one fenced block (`# >>> csb scheduled backup ...` / `# <<< csb scheduled backup <<<`); after remove: crontab byte-identical to the original. A pre-mutate snapshot of the original crontab lands in `backups/csb-schedule/`.

### 2.2 WSL caveat

- [ ] **Steps:** in WSL with cron running (`sudo service cron start`), install against a scratch store.
- [ ] **Expected:** a clearly-visible note that cron only runs while the distro runs, pointing at installing from Windows for a Windows-side store — and the install still proceeds.

### 2.3 Alpine / busybox crond

- [ ] **Steps:** `docker run --rm -v <repo>:/src alpine sh` -> `apk add python3 py3-pip git dcron`, start `crond`, venv-install csb, install schedule with `--interval 1`, wait ~90s.
- [ ] **Expected:** daemon pre-flight recognizes busybox/dcron; block installs; a cron-originated log line appears.

### 2.4 `--print-systemd` recipe

- [ ] **Steps:** `csb setup schedule --print-systemd --claude-dir <CSB_TEST_DIR>` (works on any OS).
- [ ] **Expected:** service + timer units with the same frozen argv, `Persistent=true`, the `enable-linger` warning, and explicit "printed by csb, not managed" framing. On a systemd machine (optional): paste them in, `systemctl --user list-timers` shows the timer.

### 2.5 BSD (hardware-gated -- skip if no BSD box)

- [ ] **Steps:** on FreeBSD/OpenBSD with cron enabled: HV.2 flow.
- [ ] **Expected:** daemon detection works (`ps -axo`), block installs, fires. **Record the OS/version in the issue tracker — this row is unverified-on-hardware until someone runs it.**

## Section 3: macOS launchd (hardware-gated -- skip if no Mac)

**The launchd backend has never run on real hardware.** If you have a Mac, this section is the most valuable thing you can contribute.

### 3.1 Full lifecycle

- [ ] **Steps:** HV.2 flow on macOS.
- [ ] **Expected:** plist at `~/Library/LaunchAgents/com.dazzleml.csb-backup.plist`; `launchctl print gui/$(id -u)/com.dazzleml.csb-backup` shows it loaded; prime via kickstart writes a log line; remove boots it out and deletes the plist.

### 3.2 Sleep catch-up

- [ ] **Steps:** install `--interval 60`, sleep the lid past a fire time, wake.
- [ ] **Expected:** a run fires shortly after wake (`StartCalendarInterval` coalescing) and logs.

### 3.3 SSH honesty (no GUI session)

- [ ] **Steps:** over SSH with no logged-in GUI session, install.
- [ ] **Expected:** "plist written; loads at next login" — never a false "installed and running". Status shows `plist present; not loaded`.

## Section 4: The guided question + UX (~5 min)

### 4.1 Interactive prompt

- [ ] **Steps:** `csb setup schedule --claude-dir <CSB_TEST_DIR>` in a real terminal. Try: bare Enter (-> 24h), then re-run choosing `4` -> `90` -> observe -> `30`.
- [ ] **Expected:** the four options render cleanly (no mojibake on Windows codepage 437/1252); `90` is rejected with the grammar explained and the prompt re-asks; Ctrl-C aborts with "nothing installed" and a clean exit.

### 4.2 Non-interactive refuses to guess

- [ ] **Steps:** `echo | csb setup schedule --claude-dir <CSB_TEST_DIR>` (piped stdin, no `--auto`).
- [ ] **Expected:** rc=2 with the two exact alternatives (`--auto`, `--interval`); nothing installed. No hang.

### 4.3 Help discoverability

- [ ] **Steps:** `csb setup -h` and `csb setup schedule -h`.
- [ ] **Expected:** `setup -h` mentions the schedule subaction; the leaf help explains interval grammar, anchoring, and every flag; nothing reads as filler.

## Section 5: Evidence & store hygiene (~5 min)

### 5.1 `git add -A` never sweeps operational files

- [ ] **Steps:** after an install + prime against the scratch store: `git -C <CSB_TEST_DIR> add -A`, then `git -C <CSB_TEST_DIR> diff --cached --name-only`.
- [ ] **Expected:** no `csb-logs/`, `session-backup.db*`, `.csb-backup.lock`, or `csb-fts/` staged; session data (`projects/`, `csb-live/`, `backups/`) DOES stage. User content already in `.gitignore` is preserved verbatim above the fenced csb block.

### 5.2 Run-log wire format + rotation

- [ ] **Steps:** inspect `schedule.log` lines; optionally pre-grow the file past 1 MB and trigger a run.
- [ ] **Expected:** each line is `<ISO ts> outcome=<ok|skipped-lock|error> rc=<n> duration_ms=<n> claude_dir=<path>`; oversized log rotates to `schedule.log.1` (one generation); `--status` still finds evidence across the rotation.

### 5.3 Lock contention is evidence, not error

- [ ] **Steps:** start a long `csb backup --claude-dir <CSB_TEST_DIR>` and trigger the scheduled task mid-run (GUI Run / `schtasks /run`).
- [ ] **Expected:** the losing run exits 0 and logs `outcome=skipped-lock`; no error state anywhere.

## Section 6: Per-release re-verification (run at each Claude Code release)

The feature's *reason to exist* rests on observed Claude Code behavior that can change under us. At each Claude Code version bump (or at least each csb release), re-verify:

- [ ] **6.1 The purge still exists and is still startup-driven** — Claude Code still deletes old transcripts based on `cleanupPeriodDays` during startup (i.e., an idle machine still needs an out-of-band backup). If purge behavior moved or vanished, the docs' urgency framing needs updating.
- [ ] **6.2 The purge still keys off file mtime per transcript** — csb's backup (which does not touch transcript mtimes) still doesn't accidentally extend or shorten purge timing.
- [ ] **6.3 Hook events unchanged** — PreCompact/SessionEnd/SessionStart still fire as documented (the complementary layer's assumptions).
- [ ] **Record findings** in the release notes or issue #69 follow-ups with the Claude Code version examined.

## What the automated tests DON'T cover

- Whether the real Task Scheduler / cron daemon / launchd **accepts and fires** the entry (every OS call is mocked) — HV.2, HV.4, Sections 1-3
- Console-window suppression on real Windows (flag is asserted; conhost behavior is not) — HV.2, 1.2
- Battery / missed-fire / wake-coalescing semantics (rendered XML/plist is golden-tested; OS interpretation is not) — 1.1, 3.2
- Localized `schtasks` output on non-English Windows (degrades to "readback unavailable"; needs a non-English box)
- Terminal rendering of the guided prompt and status colors across cmd/PowerShell/POSIX — Section 4
- Cross-user/cron-permission denials (`cron.allow`/`cron.deny`) surfaced verbatim
- Real elapsed-time verdict transitions (`pending` -> `ok` -> `INSTALLED BUT NOT RUNNING`) — HV.4, HV.5
- Claude Code's own purge behavior (external, version-dependent) — Section 6

## Reporting issues found

1. Note the section and step number; capture the exact command and full output.
2. Save `csb-logs/schedule.log`, the rendered artifact (`--dry-run` output), and on Windows `schtasks /query /tn csb-scheduled-backup /xml`.
3. File against issue #69 referencing this checklist and `csb -V` output.

## Cleanup

1. `csb setup schedule --remove --claude-dir <CSB_TEST_DIR>` (verify with `--status`).
2. Delete the scratch store (`<CSB_TEST_DIR>`).
3. Windows: confirm no `csb-scheduled-backup` task remains in `taskschd.msc`; delete the Section 1.4 legacy task if you created it.
4. If this machine had a production csb schedule before testing, re-install it against the real store: `csb setup schedule --interval <your interval>`.
5. Docker: containers were `--rm`; `docker image ls` if you want to reclaim pulled images (keep them if you'll re-run this checklist).
