# Naming sessions

The single highest-leverage habit for using csb. A session's **name** is what `csb list`, `csb scan`, `csb tree`, and `csb resume` all match against — so a well-named vault is something you *browse*, and an unnamed one is something you *excavate*.

Claude Code gives every session a UUID. That's fine for one project. Across dozens, over months, `3b0924e5-52f2-4eb5-8764-45c9883727d5` tells you nothing, and finding last spring's work means content-searching every transcript. Naming is what turns that back into a lookup.

## Why it matters: metadata vs content

csb can find sessions two ways, and they are not equally cheap:

| | Command | Reads | Speed |
|---|---|---|---|
| **Metadata** | `csb list <filter>`, `csb scan <term>`, `csb tree <filter>` | the SQLite index (names, projects, folders) | instant |
| **Content** | `csb search "<text>"` | every transcript, message by message | seconds to minutes |

`csb search` is the right tool for *"which session discussed the retry backoff?"* — a question only the conversation can answer. It is the wrong tool for *"where's my work on the parser?"*, which a name should have answered instantly.

**Name your sessions and the second question stops needing a search at all.**

### It pays off immediately, too

Retrieval is the long game. The short game is knowing where you are *right now*: Claude Code prints the session name at the **top-right of the input bar**, so the name you set is on screen the whole time you work.

```
                                    CLAUDE-SESSION-BACKUP__2026-7-26__add-tree-functionality
> your prompt here
```

With several terminals open across several projects -- the normal case -- that label is how you tell which window is which without typing anything. It's also the strongest argument for naming *first* rather than later: a name set at the end helps future-you, but a name set at the start helps you for the whole session.

## The convention

```
PROJECT__DATE__topic-words
```

Real examples from a working vault:

```
CLAUDE-SESSION-BACKUP__2026-7-26__add-tree-functionality
DAZZLECMD__2026-7-5__fiber-nuance-with-FQCN
DAZZLELINK__2026-7-29__no-broken-tool__fixing-relative-paths-instead
```

Three fields — **what**, **when**, **about** — answer the three questions you actually ask of an old session.

### Separators

Three tiers, coarse to fine:

| Mark | Meaning | Example |
|---|---|---|
| `__` | **field** separator | `DAZZLECMD__2026-7-5__fiber-nuance` |
| `_` | **word** separator inside a field | `fix_auth_bug` |
| `-` | **compound** — one concept spanning words | `claude-session-backup`, `no-broken-tool` |

The `_` / `-` distinction is [claude-session-logger](https://github.com/DazzleML/claude-session-logger)'s rule; `__` is the coarser tier csb queries on. They nest, so a name generated by the logger drops straight into the topic field.

### The fields

**PROJECT** — uppercase, leads the name. Uppercase is for scanning a wall of `csb list` output; csb's matching is case-insensitive, so it's cosmetic, not functional. **Leading position is not cosmetic** — it's what makes prefix queries work:

```bash
csb list DAZZLECMD              # every session for that project
csb tree "DAZZLECMD*"           # its fork families, prefix-anchored
csb resume DAZZLECMD__2026-7-5__fiber-nuance-with-FQCN
```

**DATE** — `YYYY-M-D`, compact, no zero-padding, four-digit year (`2026-7-5`, not `2026-07-05` or `26-7-5`). The four-digit year makes it unmistakably a date rather than a version or an issue number. csb stores real timestamps, so this isn't csb's source of truth — its job is to disambiguate at a glance when you revisit a topic:

```
DAZZLECMD__2026-6-18__Groupables
DAZZLECMD__2026-6-29__creating-final-FQCN-with-fibers
```

**topic** — lowercase, hyphen-compounded, specific enough to recognize months later. `add-tree-functionality` and `fixing-relative-paths-instead` pass; `updates`, `fixes`, and `working-on-stuff` don't.

## How to actually name them

### `/rename` — hand-name it, first thing

Claude Code ships `/rename`, which takes an explicit name. Type it the moment you walk into a new session, before any work:

```
/rename CLAUDE-SESSION-BACKUP__2026-7-26__add-tree-functionality
```

**Name it yourself, and name it up front.** At that moment you know exactly what you set out to do -- which project, which files, what you're trying to accomplish. Nothing else in the system knows that yet, and nothing will reconstruct it as accurately later. Thirty seconds of typing buys a name that's still meaningful in six months -- and one that labels your input bar for the rest of the session.

Called *bare*, `/rename` asks a model for a short kebab-case name (`fix-login-bug`). That's a passable *topic*, but it carries **no project and no date**, so it collides across projects and defeats the prefix queries above. Give `/rename` the full name.

### `/renameAI` — for the backlog you've already got

[claude-session-logger](https://github.com/DazzleML/claude-session-logger) adds `/renameAI`, which reads the conversation, the working directory, and the files you touched, then proposes candidates for your approval:

```
/renameAI                       # infer from context
/renameAI tree lineage feature  # weight the name toward your hint
```

This is the **remedial** tool, not the default. Its job is the pile of sessions you already have that are unnamed or badly named -- where working out what a session was even about means rereading pages of transcript. `/renameAI` does that reading for you.

It is not a substitute for naming up front. If you name first, `/renameAI` never has to guess at intent you already knew.

### Renaming later is always safe

Names aren't locked in. If the work drifts from what you set out to do, rename it -- and old sessions can be named long after the fact.

The name is written into the transcript as a `custom-title` event, and csb picks it up on the next `csb backup`. Nothing is rewritten or lost.

## A workflow that leaves a trail

Naming is step one of a routine that makes a session findable *while you're still in it*, rather than something you reconstruct later:

1. **`/rename` first -- hand-typed.** The moment you walk into the new session, before any work. You know your intent now; nothing else does.
2. **State the goal in your opening message** -- what you're trying to accomplish, which files are involved, related resources, what needs investigating.
3. **That message usually leads somewhere**: `/investigate` to gather context from issues, docs, and git history, or `/familiarize` to rebuild context on a project you've been away from.
4. **Once the background is established**, the design work: `/dev-workflow-process` for structured analysis, or a multi-round consultation like `/collabN-local`.

*(Those skills come from [dazzle-claude-code-config](https://github.com/DazzleML/dazzle-claude-code-config) -- see its [workflow doc](https://github.com/DazzleML/dazzle-claude-code-config/blob/main/docs/workflow.md). csb doesn't require them; the habit of naming first and stating intent works with or without.)*

The reason this pays off is what each step leaves behind:

| Step | Artifact | Found later by |
|---|---|---|
| `/rename` | the session name, written into the transcript | `csb list <PROJECT>`, `csb tree`, `csb resume <name>` |
| opening message | the **first block** in the session's `.convo` log | `csb search "<a phrase you wrote>"` |
| `/rename` + claude-session-logger | sesslog folder `<name>__<uuid>_<user>` | browsing `~/.claude/sesslogs/` by the same vocabulary |
| `/dev-workflow-process`, postmortems | a doc recording `**Session:** <name> (<uuid>)` | reading the doc tells you which session produced it |

That last row closes the loop in both directions. The session name gets you to the work; the doc's `**Session:**` line gets you from an artifact back to the conversation that produced it -- including its UUID, which `csb resume`, `csb show`, and `csb tree --root` all accept.

**The opening message is doing double duty.** It orients the session *and* becomes the highest-signal thing `csb search` can match on months later -- you wrote it deliberately, in your own words, describing exactly what you set out to do.

## How the pieces fit

Naming is where three independent tools meet:

- **Claude Code** owns the mechanism -- `/rename` writes a `custom-title` event into the transcript.
- **[claude-session-logger](https://github.com/DazzleML/claude-session-logger)** reacts to it -- `/renameAI` proposes good names from context, and its per-session log folders (`.convo` / `.sesslog`) inherit the name.
- **csb** consumes it -- indexes the name, makes it queryable, backs up the whole footprint (transcript + the logger's `.convo`/`.sesslog` channels), and restores it when Claude Code purges it.

Each works alone. Together, a name you set once becomes the key to a session's transcript, its tool-call log, its design docs, and its recoverability.

## What it buys you

Once names carry the convention, ordinary questions become one-liners:

```bash
csb list DAZZLECMD                      # everything for a project
csb list DAZZLECMD --sort expiration    # ...and what's closest to being purged
csb tree "CLAUDE-SESSION-BACKUP*"       # how that project's sessions forked
csb list parser                         # a topic across every project
csb resume DAZZLECMD__2026-7-5__fiber-nuance-with-FQCN
csb scan . -s                           # sessions that started in this folder
```

The names also travel: claude-session-logger uses them for its per-session log folders, so a consistent name makes `~/.claude/sesslogs/` browsable by the same vocabulary.

## Advanced: naming forks so lineage reads as a story

When a session genuinely evolves -- you're done with the thing you came for and about to start a new tool or feature -- `/fork` (or `/branch`) carries the context forward into a fresh session instead of stuffing everything into one endless transcript.

Name the fork with the **same** `PROJECT__DATE__description` format. The project stays, the date advances, the description names the *new* work:

```
DAZZLECMD__mode-symlinks
└── DAZZLECMD__2026-6-18__Groupables,Continuum,ContinuumSpace   forked 2026-06-18
    └── DAZZLECMD__2026-6-21__committing-tools                  forked 2026-06-21
        └── DAZZLECMD__2026-6-28__creating-help-lib-and-cli-libs  forked 2026-06-27
            └── DAZZLECMD__2026-6-29__creating-final-FQCN-with-fibers  forked 2026-06-28
```

That's one `csb tree --root <id>` on a real vault -- and it reads as a narrative. Same project throughout, dates climbing, each description naming the step it introduced: symlink modes led to the Groupables/Continuum work, which led to committing tools, which led to the help/CLI libs, which led to the final FQCN design. **How the work actually flowed is legible at a glance**, without opening a single transcript.

### Forking from the command line

`/fork` and `/branch` live inside Claude Code's TUI, so they only help once you're already in a session. From a shell, csb gets you the same result in one line -- because anything after `--` is forwarded straight to `claude`:

```bash
csb resume DAZZLECMD__2026-6-21__committing-tools -- --fork-session
```

That resolves the session **by name**, cds to its start folder, and launches `claude --resume <uuid> --fork-session` -- a fresh session carrying the old one's context. Then `/rename` it with the next date and description, and the new node slots straight into the tree.

This is where the convention compounds: a name good enough to find with `csb list` is also good enough to *fork from* without ever looking up a UUID.

Two things make the lineage readable, and both come from the convention:

- **The shared PROJECT prefix** keeps the whole lineage under one `csb tree "DAZZLECMD*"` query.
- **The advancing DATE** gives each node a position in time that matches the fork order the tree already sorts by -- so the visual order and the names agree instead of fighting.

Without the convention a fork tree still renders, but the nodes read as unrelated fragments and you're back to opening sessions to find out what each one was. With it, `csb tree` becomes the map of how a project's thinking developed.

Fork lineage is covered in full in [commands.md](commands.md#fork-lineage-csb-tree).

## Anti-patterns

| Avoid | Why |
|---|---|
| `fix-login-bug` | bare auto-name — no project, no date; collides across projects |
| `add-tree__CLAUDE-SESSION-BACKUP` | project trails, so `csb tree "PROJECT*"` can't anchor |
| `2026-07-26`, `26-7-26` | padded or two-digit — inconsistent with the rest of the vault; four digits read as a date at a glance |
| `updates`, `fixes`, `misc` | unrecognizable in six months |
| `STRL--Spiritism--READMEs--_git-setup` | `--` runs aren't a tier; use `__` for fields |
| `Fix Auth Bug` | spaces and mixed case fight shell quoting and filters |

## Naming sets

A **named set** (`csb set new <name> <session>...`) groups sessions that belong together — the three windows that go with one task, or a standing working set you reload often. Set names use the same separator grammar as session names (`__` field, `_` word, `-` compound), but **not** the `PROJECT__DATE__topic` shape, for two reasons:

- **Sets routinely span projects.** A working set might hold two sessions in one repo and one in a sibling library — a leading `PROJECT` field would be wrong for exactly the interesting case. Single-project groups are already findable with `csb list <project>`.
- **A date is identity for some sets and noise for others.** A standing set outlives any date; a snapshot of one moment is *defined* by its date.

So there are two shapes:

| Kind | Shape | Examples | Why |
|---|---|---|---|
| **Standing** — a working set you reload often | `PURPOSE` | `CSB-STACK`, `DAZZLE-LIBS`, `ORACLE-PAIR` | No date: it persists. Named for *purpose*, not project, because it may span several |
| **Snapshot** — a moment worth keeping | `YYYY-M-D__topic` | `2026-8-2__pre-update-restart` | Date **first**, because the date *is* the identity |

### Reserved names

Three names are rejected at creation, because the `csb set` grammar already claims them:

| Rejected | Why |
|---|---|
| `last` | names the most recent boot epoch — `csb set show last` |
| `set` | a grammar token after `csb resume` |
| bare integers (`1`, `42`, `0042`) | collide with `csb resume set <N>` index addressing |

Near-misses are fine: `last-one`, `set-aside`, and `42-things` all work. Only the exact tokens are taken.

## A note on scope

These are conventions, not rules csb enforces. csb indexes whatever name a session has — including none. Legacy and auto-generated names keep working through substring matching; the convention simply makes the *fast* queries land. Adopt it going forward and rename old sessions opportunistically; there's no migration to run.
